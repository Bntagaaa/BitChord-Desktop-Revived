# Desktop startup and memory — 1.8.3

Base: `release/1.8.3-pre-release`, `18d19325614a7f03b27b7bbdbeed934fee76230c`.

## Findings and changes

- `Main.kt`: cookie installation, player/AppUi registration, logging and InnerTubeX/PoToken wiring remain ordered before shared UI usage. No native decoder/model dependencies were removed. The graphics default is captured before Presence writes its install ID.
- `DesktopApp.kt`: startup previously scanned Local Music, initialized the analyser and verified downloads before calling `loadHome()`. Home now starts after account activation independently of filesystem verification. Its existing concurrent primary/Recently Played/supplementary shelves, continuation handling and deduplication remain. Refresh cancels the previous Home job, and generation checks still reject stale responses. Account/profile/session changes invalidate Home.
- `DesktopLocalMusicSession.kt`, `DesktopLocalMusic.kt`, `DesktopLocalMusicWatcher.kt`: first Local Music visit starts a cancellable scan and watcher. The window retains the result across navigation. Folder/filter changes replace the observation; a mutex serializes scans and invalidates the cached revision. Subscription and completed watcher registration precede the scan so events during scanning are not lost. Watchers debounce bursts, notice overflow/directory changes, register new subdirectories within the original depth budget, and close on disposal. A replacement waits for the prior watcher to close. No persistent filesystem index or migration was introduced.
- `DesktopListeningStats.kt`: removed the summary computed during composition and both unconditional startup effects. Replay loads on opening, off the UI thread, with a loading state. A bounded three-period cache invalidates on successful recording, clearing, or calendar-day changes. Coroutine cancellation prevents an obsolete period from publishing after a new selection. Statistics remain local-machine history, as before; no account ownership/data migration was invented.
- Download verification runs on IO independently of Home; removal merges complete records against the original snapshot so a newly completed replacement survives. Clicking download before verification completes checks an existing record on IO and permits retry if its file is missing. Existing playback-side `savedFile` validation remains.
- `YtMusicRepository.library(full)` defaults to full loading for existing/Android callers. Desktop startup loads likes and paged playlists, preserving the sidebar, playlist picker and background liked-ID synchronization. Added songs, albums, artists, subscriptions and podcasts wait for Library navigation. A successful full result is reused; account/profile/session changes invalidate it. Library state is keyed by account/profile and old liked synchronization is canceled/identity-guarded. First Library navigation may refetch likes/playlists: this is a deliberate correctness trade-off instead of a new persistent account cache.
- `DesktopAppearanceSettings.kt`, `DesktopGraphicsProfile.kt`: persisted FULL/BALANCED/PERFORMANCE profiles. Existing stores retain FULL and their individual toggles. Empty stores choose PERFORMANCE for <=2 logical CPUs or <=4 GiB known RAM; otherwise BALANCED. Unknown GPU capability is not inferred from CPU count. Detection runs once; manual selections are retained. No continuous AUTO adjustment. BALANCED uses 65% of existing Haze radii and opaque app chrome; PERFORMANCE uses opaque dynamic surfaces; FULL retains existing radii. Sidebar opacity and native Mica behavior are unchanged.
- All desktop Haze paths use the shared policy (including the low-level Search surface); desktop settings now also forward the effective blur override into shared player settings and lyrics. Reduce dynamic blur takes priority over every profile and area toggle. Saved area preferences are not rewritten, so disabling the override restores them. Real Windows rendering still needs manual verification.

## Memory/lifecycle audit

The changes avoid retaining Replay's aggregate lists before Replay is opened and avoid building/retaining secondary Library collections during startup. Local Music watcher handles and scanned tracks are absent until first use. Obsolete Home jobs are canceled rather than just retaining them until their network calls finish. These are source-supported reductions in unnecessary work; no numerical RAM saving is claimed.

`DesktopArtworkCache` already uses a byte-budget LRU (heap/6, clamped to 32–128 MiB). Canvas lookup also has an existing bounded LRU. No speculative reduction to their budgets was made. Track analysis model/BeatTracker initialization is already lazy; the redundant explicit startup analyser initialization was removed. Model unpack and analyser initialization have diagnostic milestones. Audio decoder closing, crossfade buffers, JavaFX PoToken cleanup, ONNX sessions, Discord, tray, media keys and MPRIS were inspected but not rewritten without runtime evidence of a leak. JVM `-Xmx512m` and G1 options are unchanged. No forced GC.

## Diagnostics and measurement protocol

Opt in only in the benchmark shell (unset afterwards):

Linux:

```sh
export JAVA_TOOL_OPTIONS="-Dbitchord.startupDiagnostics=true"
./gradlew :desktopApp:createDistributable
# Benchmark the packaged process, not Gradle configuration/compilation:
desktopApp/build/compose/binaries/main/app/BitChord/bin/BitChord 2> startup.log &
app_pid=$!
ps -p "$app_pid" -o pid,etimes,rss,pcpu
jcmd "$app_pid" GC.heap_info
# For a native breakdown, opt in at process creation with:
# JAVA_TOOL_OPTIONS='-Dbitchord.startupDiagnostics=true -XX:NativeMemoryTracking=summary'
# jcmd "$app_pid" VM.native_memory summary
unset JAVA_TOOL_OPTIONS
```

Windows PowerShell:

```powershell
$env:JAVA_TOOL_OPTIONS = '-Dbitchord.startupDiagnostics=true -XX:NativeMemoryTracking=summary'
.\gradlew.bat :desktopApp:createDistributable
$app = Start-Process '.\desktopApp\build\compose\binaries\main\app\BitChord\BitChord.exe' -PassThru
Get-Process -Id $app.Id | Select-Object Id,WorkingSet64,PrivateMemorySize64,CPU
jcmd $app.Id GC.heap_info
jcmd $app.Id VM.native_memory summary
Remove-Item Env:JAVA_TOOL_OPTIONS
```

Fixed, one-shot phase names report monotonic elapsed time, JVM process uptime, used heap and committed heap. They never include account identifiers, tokens or cookies. Disabled diagnostics allocate no event collection or drawing observer. `window-created` means composition has the AWT window. `shell-first-draw` is observed after Compose draws shell content, **not** compositor presentation or an interaction-readiness timestamp. `home-primary-received` is distinct from `home-primary-content-draw`. First usable UI must also be verified with a real interaction. A first-run welcome overlay is part of that experience and must be held equal between comparisons.

RSS is total resident process memory (Linux `ps` reports KiB), not JVM heap. NMT is an optional JVM/native breakdown and may omit third-party native allocations. Subtracting heap from RSS is not an accurate measurement of native memory. Do not force GC during comparisons.

For base/optimized comparison, use separate sequential builds of the recorded base and this branch on the same machine/JDK/build type and renderer. Keep identical profile, account, folder contents, network and preference snapshots. Never delete real user data to produce a cold run. Use isolated test preferences or a copied benchmark profile. Record five fresh-process cold/cache-controlled and warm/persisted runs and report median/range. Record startup, primary Home draw, idle at a fixed interval (e.g. 60 seconds), and CPU/RSS/heap during a fixed track's playback. OS cache state must be recorded; a fresh process alone is not a cold filesystem cache. Perform measurements without concurrent builds/tests.

Navigate Library, Local Music (including adding/removing folders and burst file changes), Search, Replay periods, Quick Search, lyrics, floating player and profile flyouts. Exercise refresh and account switching while requests are pending. Compare all three profiles, then toggle Reduce dynamic blur on/off with mixed area preferences. Verify actual visuals, focus, playback and cancellation on Windows and CachyOS, including Mica, tray, MPRIS and media controls.

## Validation and limitations

Cloud host: Linux 6.18.55 x86_64, Debian userspace, Java 21.0.9; cgroup budget 4 CPU cores/32 GiB. Xvfb 1440x900. GL context creation fails and Skiko falls back; no real audio device, authenticated accounts or Windows session is available. YouTube DNS requests fail in this runtime. These conditions do not support meaningful cold/warm/playback or hardware-blur comparisons.

An earlier candidate's packaged signed-out FULL run observed shell draw at 2,259 ms after instrumentation entry (process uptime 2,438 ms); used heap at that event was 61,448,624 bytes. A later sample at process age 25 seconds reported RSS 490,092 KiB and heap used 88,902 KiB (`ps`, `jcmd GC.heap_info`). This is **not** a base-versus-change comparison or a target-machine benchmark. The final first-run profile initialization was refined afterwards. Baseline/post-change performance and percentage savings remain pending. No native-memory figure was measured.

The packaged application rendered its welcome screen, accepted Skip, opened Local Music, and showed scan/watcher milestones only on that first visit (about 37 seconds after launch in the manual smoke run). Settings navigation also worked. This validates the deferred path, not the full authenticated feature matrix or every rendered blur surface.

Commands used in this cloud checkout (the local Gradle launcher selects the installed JDK, proxy and trust store):

```sh
DISPLAY=:99 python3 /workspace/.cloud-setup/gradle.py \
  -I /workspace/.cloud-setup/test-runtime.gradle \
  :shared:jvmTest :sharedUi:jvmTest :desktopApp:test \
  :desktopApp:createDistributable -Pbitchord.version=test-visua --continue
```

The local init script sets test JVM `user.home` and `java.util.prefs.userRoot` to isolated writable `/workspace/.cache` directories. Initial attempts using the default read-only home failed; reruns with isolated paths passed. This is a test-environment correction, not disabled assertions. Tests use fake scan events, cancellation, temporary directories, revision caches, record replacement and the profile/area/master-override matrix. Existing filter, sorting, playback, account parser and UI suites are retained. Live account switching and network request behavior still need authenticated manual testing.

The repository's `Check` workflow runs Linux and Windows JVM tests/distributables on pull requests. CI status is recorded in the PR rather than inferred from local results. Native Windows execution and installer formats cannot be validated on this Linux machine. Keep the PR as Draft until those checks and target-machine performance measurements are reviewed.
