# Unified desktop video engine — backend gate

**Status:** backend under evaluation. The probe runs outside the production playback paths. Shipping an engine requires a compositor-integrated frame on Linux and Windows with the existing player effects.

## Candidate evidence

| Route | Evidence and decision |
| --- | --- |
| GStreamer VA-API → DMA-BUF → native Wayland sink | The Intel iHD decoder negotiated tiled NV12 DMA-BUF at decoder output and at the sink. The KDE native Wayland window showed both fixture orientations. This proves hardware decode and a native buffer path to the sink on this host. It does not measure copies inside the graphics driver or compositor. The sink owns its own Wayland surface, which is outside the Compose draw graph. |
| GStreamer VA-API → DMA-BUF → EGL/OpenGL → X11 | The probe negotiated DMA-BUF at the GL sink boundary and displayed live video in a Compose window under XWayland. The native AWT child bypassed the rounded clip and bottom gradient, including with Compose interop blending enabled. That rules out a heavyweight native child as the replacement for the current composited video surfaces. |
| GStreamer VA-API or software → OpenGL texture → Skiko | GStreamer supports wrapped/shareable GL contexts, GLMemory and explicit sync metadata. A backend would need access to Skiko's actual render-thread context, compatible EGL/GLX context sharing or a DMA-BUF import with supported modifiers, and a borrowed texture lifetime spanning Skia submission and GPU use. The public `makeGL` texture wrapper alone supplies none of that coordination. This route remains a candidate. |
| GStreamer Vulkan | A native Vulkan sink exists. Using it as a child surface has the same compositor boundary. A shared-image route needs device compatibility, external-memory and fence interoperability, plus a Skiko import path that works on the selected renderer. No Vulkan path was verified. |
| GStreamer D3D11 / D3D12 | The separate Windows probe mode requests D3D11 device memory end to end or uses a software decoder plus GPU upload. A native HWND sink requires a Windows runtime test and cannot take part in Skia masks, blur or palette sampling by itself. GStreamer can expose D3D11 textures through appsink. The resolved Skiko bindings expose a Direct3D render-target wrapper but the public backend-texture import is GL-only. D3D11-to-D3D12 sharing needs a compatible adapter, shared resource and fence ownership and a Skia-side import. D3D12 decode/presentation is a driver-dependent option after those basics work. No physical Windows GPU runner was available. |
| Direct libmpv | The direct render API control used a native SDL Wayland OpenGL context, observed `hwdec-current=vaapi` and recorded successful buffer swaps. This bypasses MediaMP and shows that libmpv can decode and draw into an application-owned framebuffer on this host. The test supplies its own context and cannot establish that a current Skiko composition can import the result or render it on Windows. Swap return is not a compositor timestamp. |
| FFmpeg with native video presentation | Existing JavaCPP/FFmpeg dependencies simplify deployment and already implement source headers, HLS and timestamps. A hardware-frame backend would still need VA/DMA-BUF import on Linux, D3D texture import on Windows, color conversion, fences and context-loss handling. The existing software path remains the production baseline. No FFmpeg GPU presentation experiment was run. |

GStreamer references cover [VA-API decoding](https://gstreamer.freedesktop.org/documentation/va/vah264dec.html), [DMA-BUF and modifiers](https://gstreamer.freedesktop.org/documentation/additional/design/dmabuf.html), [native window embedding](https://gstreamer.freedesktop.org/documentation/video/gstvideooverlay.html), [GL context and synchronization](https://gstreamer.freedesktop.org/documentation/additional/design/opengl.html), [D3D11 sink and texture APIs](https://gstreamer.freedesktop.org/documentation/d3d11/d3d11videosink.html) and [D3D12 sink](https://gstreamer.freedesktop.org/documentation/d3d12/d3d12videosink.html). The alternative uses the [libmpv OpenGL render API](https://github.com/mpv-player/mpv/blob/master/include/mpv/render_gl.h).

## Contract for an engine after the gate

- A window-independent, application-owned engine hands out closeable surface leases. A session key includes the resolved source and authorization/header identity, rendition and output requirements, loop/seek behavior, and clock owner and track instance. Share compatible artwork and backdrop consumers or two presentations of the same clock. Close the session when the last visible lease leaves, with bounded transition handoff if needed. Own native open, seek and shutdown inside one serialized lifetime so cancellation can never publish a late decoder.
- A backend delivers fenced native frame leases; the compositor returns the lease only when it is safe to recycle. Favor a bounded latest-frame mailbox and apply backpressure at pools and queues. Quantify memory with actual resolution/format and decoder reorder depth. Run palette extraction on a small, rate-limited sample of the shared frame. Keep the original still artwork behind the video until the renderer confirms a usable frame.
- Keep source resolution, decoder readiness, first decode, first renderer submission, and compositor presentation separate. Give each startup attempt a deadline. Close the failed pipeline and release its callback/surface ownership before a single controlled software fallback. Report the actual decoder, negotiated frame memory, render API, frame drops, and the strongest observable readiness signal. Sanitize signed URLs and headers in diagnostics.
- Read BitChord's existing seek serial, sampled playhead, pause, buffer state, and rate for music video. Select video streams only. Window/viewport visibility controls attachments independently of audio. Preserve Home when Now Playing changes placement. Main, fullscreen and PiP surfaces lease a compatible session without rebuilding navigation.
- Software rendering must have a budget of its own, including explicit ownership of decoded storage until the renderer releases it. Smoke-tested GStreamer BGRx native output on Linux is useful fallback evidence for a native sink. It does not yet supply a compositable fallback for BitChord UI.

## Deployment and acceptance

The probe requires GStreamer core/base development files and the playback plugins listed in the [benchmark instructions](unified-video-engine-benchmarks.md). The libmpv control additionally requires SDL3 and libmpv development files. These are development-only dependencies. A production GStreamer candidate must package a tested plugin inventory and plugin scanner on Windows and either bundle or declare compatible runtime and graphics driver dependencies on Linux. Verify both portable and installed distributions in a clean environment.

Backend acceptance still requires a same-compositor texture and visual inspection on real Wayland and Windows systems, resize and context loss, per-session software recovery, HLS and audio-clock behavior, and the application-level scenarios in the benchmark plan. Driver and graphics API support must follow measured results.
