# BitChord 1.9.3 — long-session memory and Home lifecycle

This performance-only change targets the Kotlin/Compose desktop, independently of the
lossless/lyrics/download fixes in PR #143. It does not change the Flutter rewrite.

## Home: discard on leave, not based on a memory threshold

- On **Home → New / Search / Library / Downloads / any other top-level page**, invalidate
  Home's feed request and cancel outstanding child work. Clear saved shelves, continuation
  token, deduplication set, Recently Played loading state and derived Top Picks.
- The same behavior applies when Home is covered by a **detail page (artist/album/playlist)**,
  Settings, Replay or the separate Mood Grid.
- **Exception: opening expanded/fullscreen Now Playing while on Home retains its feed,
  pagination and scroll position.** Closing the player returns instantly without refetch.
  A real destination change still discards Home even if the player overlay is open.
- Increment the Home request generation, preventing late network callbacks from restoring
  discarded content. Pagination results are guarded by generation on both success **and failure**.
- Drop the Home LazyListState so returning Home starts from the top and fetches fresh data.
- The playback engine, queue, liked songs, user playlists, downloads, history, account login,
  and Back navigation history are **not** Home data and remain untouched.
- This happens at any RSS value. The 650-MiB pressure policy is independent.

## Main window / tray / PiP lifecycle

- **Fullscreen Now Playing within the main window is not a disposal trigger.**
  The Home feed and scroll remain mounted while that overlay opens and closes.
- **Close to system tray** removes the entire main Compose `Window` from the
  application composition (not just `Window(visible = false)`). Its native
  AWT/Skia peer, page models and remembered UI state are disposed. The process
  retains only the playback service, platform media controls, tray and other
  strictly background facilities. A tray activation creates a fresh UI.
- **Open PiP** mounts the independent `DesktopPipHostWindow` first; once its
  native window is ready, the main window is removed in the same way. PiP's
  position, lyrics and controls read the process-owned playback service, not a
  callback closure held by the disposed main UI.
- **Return from PiP** destroys the floating window and remounts the main UI.
  It reconnects to the SAME decoder, source stream, playhead, queue and song.
  No new engine may be created merely because a window was restored.
- The same process-owned service handles media keys, MPRIS, the tray menu,
  sleep timer and end-of-track/next/previous while no main UI exists.
- **Quit** is deliberately different: it shuts down the decoder, backend media
  controls and remaining service resources.
- Existing playlist/album pages and Home data are deliberately not preserved
  when the entire main window is destroyed; login credentials, history and
  playback/queue data persist separately.

### Tray/PiP acceptance checks

1. Play music, close the main window to tray: audio continues, the main
   Compose/Skia/AWT window is gone, tray Play/Pause and Next still work.
2. Reopen from tray: the song, playhead, queue and account are unchanged. The
   main UI reloads its pages; it must not restart audio from zero.
3. Enter PiP: wait for the floating native window to appear, then confirm
   the main window is no longer mounted. Play/Pause, seek, Next and lyrics in
   PiP must continue working after the main UI is gone.
4. Restore from PiP: no second audio engine and no audible interruption.
   Close PiP with close-to-tray enabled: audio continues without any main UI.
5. Open expanded/fullscreen Now Playing inside the main window and close it:
   **Home is not discarded**, retains its scroll, and does not refetch.
6. Explicit Quit stops audio and terminates process cleanly.
7. Validate on KDE/CachyOS/Wayland and Windows, including login, system media
   keys and changing audio device while hidden.

### Limitations to validate manually

The playlist/queue advances in the background without its main-window callbacks;
AutoPlay network top-up and Listen Together synchronization still need explicit
end-to-end verification after long hidden sessions. Passing CI alone does not
prove these UI-independent features work in a live account.

## Long-session retention reductions

- The JVM AutoMix analysis working set keeps **64** recently accessed in-memory analysis
  records (results are persisted separately on disk).
- AutoMix's failed-track tracking keeps up to **256** IDs; the persisted-analysis
  negative/positive file-lookup hints retain at most **1,024** IDs.
- The media disk-cache path is deterministic from a URL hash. An unbounded process-lifetime
  map of URLs to these paths was removed; the disk cache and limits remain.
- Canvas video frame producers use three reusable byte buffers in place of allocating
  a full-frame `copyOf()` each frame. Backdrops and mesh callbacks that retain a frame
  receive independent snapshots, so their image is not silently rewritten by the ring.
- Artist/album motion artwork stops opening or decoding video while the main window is
  hidden (in the system tray).
- If RSS exceeds 650 MiB and no inactive page can be evicted, native/image cache trimming
  may still occur, but at most once every two minutes. This avoids repeatedly forcing
  a stop-the-world collection on each five-second pressure check.

## What remains unproven

The code audit identified unbounded structures and large per-frame allocations; it
**does not prove** that the user's observed RAM slope is a persistent memory leak.
Only a comparable packaged long-session run can do that. Native driver/Skia/FFmpeg
allocations are not necessarily visible in the JVM heap.

### CachyOS/Linux measurement

Find the actual app JVM/launcher PID (not Gradle):

```bash
ps -eo pid,rss,cmd | grep -E 'BitChord|bitchord' | grep -v grep
bash scripts/profile-desktop-memory.sh <PID> 3600 30
```

The script writes `process.csv` with RSS, PSS, peak RSS, private dirty memory,
swap, threads and open FDs; when a JDK with `jcmd` is available it also collects
optional heap and NMT snapshots every approximately five minutes.

Repeat with the **same app build, settings and window size** in these scenarios:
1. Home idle, no music, 30–60 min; navigate Home → New → Home periodically.
2. Music playing, Canvas disabled, 60 min.
3. Same playlist, Canvas enabled, 60 min.
4. Same playlist, AutoMix enabled, 60 min.
5. Hidden to tray for 30 min while playback continues, then restore.

Compare the memory *slope after warm-up*, not only the process's initial RSS.
A rise that plateaus may be JVM/native caching; continuous retained growth in
heap, PSS, native allocations or FD/thread counts needs a new investigation.

### Acceptance

- Leaving Home releases the in-memory feed even below 650 MiB; returning Home
  visibly fetches the first page and starts at scroll position zero.
- Fullscreen Now Playing opened from Home retains its feed/scroll and does not trigger a
  reload when closed. Back navigation still works; playback/queue/history/login remain intact.
- Canvas animation does not regress visually; no reused buffer modifies a
  frame captured for the background mesh.
- Desktop Linux/Windows tests and packaging pass.
- A live long-session RSS/PSS profile is required before claiming leak-free
  operation or a precise percentage memory improvement.
