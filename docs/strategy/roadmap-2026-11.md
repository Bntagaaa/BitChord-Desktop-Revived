# Revived: 7 / 30 / 90-day roadmap

Baseline: source audit on **9 November 2026, Asia/Jakarta**. [Evidence and source index](competitive-audit-2026-11.md) · [Benchmark protocol](benchmark-protocol.md).

These horizons are planning windows from kickoff, not delivery promises. Priorities reflect user-facing reliability and verified implementation evidence, not competitor feature counts. P0 = release-blocking/user trust or foundational validation; P1 = major daily-use improvement; P2 = longer-term differentiation/expansion. Success numbers below are **proposed acceptance targets**, not measured current performance or guaranteed improvements. One maintainer should work on one risky playback/UI change at a time.

## Execution policy

Use dedicated branches based on current 1.9.2 and focused PRs. Record before/after evidence, tests, CI, user-visible effect and limitations. Preserve license and attribution. Changes to optional runtimes, audio engine, renderer, backend service operation or release support are decision points requiring an RFC/approval appropriate to risk. Keep reworked separate. No auto-merge.

Review the roadmap weekly against new bug evidence. If benchmarks show the current architecture meets user budgets, invest in reliability and differentiation instead of forcing architecture work. If it does not, compare several incremental fixes before considering a rewrite.
